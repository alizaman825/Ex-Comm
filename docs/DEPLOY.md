# Deployment

Backend (Express API) on **Render**, frontend (Next.js) on **Vercel**, database on **MongoDB Atlas**.

The browser only talks to the Vercel site. Next.js proxies `/api/*` to the Render API (`BACKEND_URL`), so the session cookie stays first-party.

## 1. Backend on Render

1. Render dashboard → New → Blueprint → pick this repository. `render.yaml` creates the `ex-comm-api` web service (root `backend`, health check `/api/health`).
2. Fill in the two prompted values:
   - `MONGO_URI`: the Atlas connection string (database `excomm`).
   - `CORS_ORIGIN`: the Vercel URL from step 2 (it can be updated after the first deploy).
3. `JWT_SECRET` and `JOB_KEY` are generated by Render. The first start seeds sample data (about a minute).
4. Check: `https://<service>.onrender.com/api/health`.

Free instances sleep after 15 minutes idle; the first request after that takes about a minute.

## 2. Frontend on Vercel

1. Vercel → Add New → Project → import this repository.
2. Root Directory: `frontend` (framework preset Next.js is detected).
3. Environment variable: `BACKEND_URL=https://<service>.onrender.com`.
4. Deploy, then put the resulting `https://<project>.vercel.app` into Render's `CORS_ORIGIN`.

## 3. Atlas network access

Render's free plan has no fixed outbound IP, so allow `0.0.0.0/0` under Atlas → Network Access and rely on a strong database user password.

## 4. Keeping prices and stock fresh on the free plan

Render's free instance sleeps after 15 minutes idle, and the scheduled catalog-sync/price-check jobs run as in-process timers - while the dyno is asleep, they don't fire, so listings can silently go stale (seen in practice: a month without a refresh). `.github/workflows/daily-refresh.yml` fixes this from outside Render: every 15 minutes it hits `/api/health` (wakes the dyno if needed) and calls `/api/jobs/catalog-sync` + `/api/jobs/price-check`, so the data keeps moving even if nobody visits the site. (This repo is public, so GitHub Actions minutes are free and unlimited; a private repo would need a longer interval to stay within its monthly minutes.)

Add these repository secrets (GitHub → Settings → Secrets and variables → Actions) or the workflow has nothing to call:
- `RENDER_API_URL`: the deployed API's base URL, e.g. `https://ex-comm-api.onrender.com`.
- `JOB_KEY`: the same value Render generated for the service's `JOB_KEY` env var (Render dashboard → service → Environment).

Without these secrets the jobs still run on their normal cron *while the dyno happens to be awake*, but gaps longer than a day are expected again.

## 5. Contact form email notification (optional)

The Contact page (`/contact`) always saves a message and always shows the visitor success, whether or
not this is set up - it only controls whether the owner also gets an email.

1. [resend.com](https://resend.com) → sign up with the inbox you want notifications sent to → create
   an API key (Dashboard → API Keys).
2. Render → `ex-comm-api` service → Environment, set:
   - `RESEND_API_KEY`: the key from step 1.
   - `CONTACT_RECIPIENT_EMAIL`: the **same email address you used to sign up for Resend**. On Resend's
     free tier, without verifying your own custom domain, you can only send from the shared
     `onboarding@resend.dev` address to the address that owns the API key - exactly this case (a
     notification to yourself). Sending to a different address, or from a different `RESEND_FROM_EMAIL`,
     needs a verified domain in Resend first.
   - `CONTACT_IP_HASH_SALT` is already generated by `render.yaml`; no action needed.
3. Leave `RESEND_API_KEY` or `CONTACT_RECIPIENT_EMAIL` unset to disable the email notification entirely
   - messages are still saved and visible via `GET /api/contact` (`x-job-key` header).
